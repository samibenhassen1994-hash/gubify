# Community Images Phase 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a Community owner upload and display one deterministic, optimized Cloudinary image with atomic Firestore publication and strict Rules validation.

**Architecture:** `Community Settings -> CommunityImageService -> CommunityImageRepository/CommunityRepository -> Worker, Cloudinary, Firestore`. Image selection and processing remain client-side, upload signing comes from the existing Worker, and root/public metadata is committed in one Firestore transaction.

**Tech Stack:** Flutter, Firebase Auth, Cloud Firestore, `image_picker`, `http`, `image`, Cloudinary signed uploads, Firestore Rules emulator.

**Spec:** `docs/superpowers/specs/2026-08-26-community-images-phase1-design.md`

## Global Constraints

- Original file limit is exactly 20 MiB and is checked before reading bytes.
- Gallery only; orient, center-crop, resize to 512 x 512, JPEG quality 82.
- Cloudinary cloud is `s3yauoza`; deterministic public ID is `community_<communityId>`.
- Signed upload uses the existing Worker; no Cloudinary secret or SDK in Flutter.
- Root and `communityPublic/{slug}` metadata update atomically.
- No remove/delete cleanup, index changes, unrelated refactor, commit, push, or merge.
- Preserve every pre-existing dirty working-tree change.
